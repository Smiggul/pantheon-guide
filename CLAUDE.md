# pantheon-guide — Claude Code Context

## What this is
A League of Legends pre-game itemization and rune guide. Single-page React app (no backend, no router, no state library). User selects champion → role → enemy class → ahead/behind → gets item recommendations + interactive rune page.

## Stack
- React 19 + Vite 8, JSX only, no TypeScript
- 100% inline styles + src/theme.js for style tokens
- No CSS framework, no Redux, no external UI libraries
- Run: `npm run dev` from project root
- **Working files go on D:, in `.scratch/`** (gitignored): downloads, test scripts, screenshots, research output. Never the C: temp scratchpad; C: is the small system drive (the user, 2026-10-22). Agent worktrees live in `.claude/worktrees/`, also gitignored.

## Key files
- `src/App.jsx` — all UI (~3000 lines): helpers, CLASSES, RUNE_TREES, RunePage, panels
- `src/ForgeCards.jsx` + `src/forgeStyle.js` — the redesigned build page's cards (item set timeline, situational, skills, compact runes, the finding sentence, the segmented control), shared by the build page and `InGameView.jsx`; forgeStyle holds the tokens and the colour maths (see "Redesign" below)
- `src/data/champs/*.js` — one file per champion (rune constants + default-exported champ object); `index.js` assembles the CHAMPS array. Shared rune constants must be exported/imported (e.g. RENEKTON_TOP_DEFAULT_RUNES) — a `vite build` does NOT catch a missing cross-file constant, it only fails at runtime
- `src/data/runeHelpers.js` — `I(name, why)` item-entry helper used by all champ files
- `src/theme.js` — all colour tokens and reusable style objects
- `electron/main.cjs` — desktop shell; serves dist/ over app:// (MIME map required for module scripts). `npm run dist:win` builds installer + portable exe into release/
- `public/ddragon/` — Data Dragon assets (populated by helpers/setup_ddragon.py)
- `helpers/setup_ddragon.py` — run after each patch: `python helpers/setup_ddragon.py` (no args = pulls the latest patch from **Riot's own Data Dragon CDN**, incremental — skips images already on disk; `--force` re-downloads; `--mirror` forces the noxelisdev/LoL_DDragon GitHub mirror instead, which is also the automatic fallback if the CDN is unreachable). It used to read the mirror by default, which lagged a full patch on 26.19 and silently re-pulled the previous patch — see the auto-updater note below. Passing a dragontail `.tgz` path still works as offline fallback. NEVER `git clone` the mirror — it is ~10 GB. After running it, regenerate every file generated from those assets, in the order the patch workflow uses: `node helpers/gen-lcu-data.mjs` (client export ids), `node helpers/gen-sr-items.mjs` (`public/ddragon/data/sr-items.json`, the Build Forge Rift item allowlist), `node helpers/gen-summoner-spells.mjs` (spell map + icons), `node helpers/gen-champ-skins.mjs` (`src/data/champSkins.js`, the Forge random-splash pool) and `node helpers/gen-abilities.mjs` (`src/data/abilities.js`). All of them pin to `public/ddragon/version.txt`, NOT always-latest, so outputs always match the bundled assets; since 2026-10-21 that includes gen-lcu-data's CommunityDragon rune ids (`/16.21/`, falling back to `/latest/` with a warning if a new patch's folder is not up yet), which used to read `latest`. gen-abilities' ability **text** is pinned too (since 2026-10-22): it is Riot's own tooltip text from the game's string table, with every `@placeholder@` resolved from the champion's game data (per-rank values and Riot's tooltip formulas), both read from CommunityDragon's folder for the bundled patch (`/16.21/game/en_us/data/menu/en_us/lol.stringtable.json` and `/16.21/game/data/characters/<dd>/<dd>.bin.json`); names, icons, cooldown, cost and range still come from Data Dragon. It replaced Meraki, which serves only `latest`, had stopped at patch 25.15 and had no Locke, Yunara or Zaahen. About 1% of numbers stay unresolved, almost all runtime read-outs (Aurelion Sol's current Stardust, Aphelios's weapon queue), and are dropped from the sentence; `--list-unresolved` names them, `--cache <dir>` keeps the downloads for debugging. Riot hides some names behind FNV-1a hashes (`{6c540a3a}` = `executetooltipcalc`) and the `mStat` stat ids are not published: the map in the generator was read off abilities that use each id, and an unknown id is left unresolved rather than guessed. **`counterPicker.js` derives the dash/heal/shield traits from this text**, so its patterns follow Riot's wording ("restores 40 Health", "charges forward", "pulls himself to"); re-run a before/after tag comparison if either side changes. gen-champ-skins and gen-abilities refuse to write a partial or degraded file (exit 1, previous file kept): gen-abilities exits on a missing string table, more than 3 champions without game data, or more than 6% unresolved numbers. `gen-skin-themes.mjs` is roster data, not patch data: run it when adding a champion, BEFORE gen-abilities and gen-champ-skins, which take their champion list from `src/data/skinThemes.js`.
- `src/data/matchupAdjust.js` — proposes build changes against the specific lane opponent, from their own facts rather than their class (see "Matchup adjustments" below). Pure logic, called by gamePlan.js.
- `src/data/gamePlan.js` — the ONE item recommendation, ordered by phase (Lane / Mid game / Late game): lane answers, team answers, Ahead/Behind order and boots timing. The plan strip under the "vs" readout, the build card's core order and the exported item set all come from it (see "Game plan + boots timing" below). `src/data/bootsTiming.js` is generated by `npm run gen:boots` (helpers/gen-boots-timing.mjs).
- `src/data/matchupStarts.js` — the lane starts players buy (per champion-role and per lane matchup), each support role's World Atlas set and each jungler's most common pet. Generated by `npm run gen:starts` (helpers/gen-matchup-starts.mjs, report-only, never in CI); read by `lcuExport.js` (`dataStartsFor`) and `junglePets.js` (see "Matchup-aware starters" below).
- **Data checks** — `npm run check:runes` (rune-row legality across all classes, alts and overrides), `npm run check:items` (every recommended item is sold on Summoner's Rift AND has a client export id — when it reports a missing export id, run `node helpers/gen-lcu-data.mjs`), and `npm run audit:builds` (every role's corePath against lolalytics' most common opening; report-only). Run all three after any build-data edit: `vite build` and the champion-validator catch none of these problems.
- **Auto patch updater** — `helpers/check-patch.mjs` compares the bundled version to the official Data Dragon API; `.github/workflows/patch-update.yml` runs it on a cron (**twice a day**, 06:17 and 18:17 UTC, since 2026-10-21; it was every 3 days and let 26.21 sit unnoticed. A no-patch run exits at the version check in seconds. The schedule only fires from the default branch, `frge-gg`) and, on a new patch, runs setup_ddragon, gen-lcu-data, gen-sr-items + gen-summoner-spells + gen-champ-skins (one step; Riot-only, a failure fails the run), patch-diff and patch-notes (the PR body), gen-abilities, check-sr-items and the build, and opens a PR (branch `auto/ddragon-<ver>`). **Until 2026-10-21 it ran only setup_ddragon + gen-lcu-data**, so `sr-items.json` sat stamped 16.17.1 for four patches (its 222 items happened not to change), `champSkins.js` missed 19 skins released since, and `abilities.js` carried pre-26.21 cooldowns (Darius Q, Lee Sin W). gen-abilities runs after the report exists because it soft-fails: on a CommunityDragon outage, or a patch folder CommunityDragon has not published yet, it keeps the previous file and appends an "Ability text not regenerated" section to the PR body instead of failing the update. **Any generator that writes under `src/` must also be listed in the PR step's `add-paths`** (now `lcuData.js`, `champSkins.js`, `abilities.js`), or its output never reaches the PR. The PR still needs a human pass for new champions / item reworks / meta shifts before merge. One-time repo setting required: Actions → General → allow GitHub Actions to create PRs (enabled). **It never produced a PR until 2026-10-19.** The "Fold the notes into the report" step built a separator with a multi-line `printf` that put `---` at column 0, which terminates a YAML block scalar, so bash only ever received two lines and failed with `unexpected EOF`. The runs listed as successes were the no-op ones that exit at the version check; every run with real work died at that step. Fixed, and verified end to end by dispatch: all 19 steps green, PR #2 delivered 16.20.1, byte-identical to a hand-run update. Two traps to remember when editing it: never put content at column 0 inside a `run: |` block, and a green run in the list proves nothing on its own — check that a PR actually opened. The repo allows **rebase or merge-commit** merges, not squash.

## Architecture rules (must follow)
1. All sub-renderers inside RunePage MUST be called as plain functions `{primaryContent()}` NOT JSX components `<PrimaryColumn />` — the latter causes React to remount on every render, breaking images and state
2. After any edit to champion data objects, validate brace balance: `python3 -c "d=sum(1 if c=='{' else -1 if c=='}' else 0 for c in open('src/App.jsx').read()); print('Balance:', d)"`
3. `runeImg` must guard against null src: `{src && !imgFail(ek) ? <img src={src} onError={...}/> : <Fallback />}` — never `<img src={null}>`
4. All rune/perk images in `/ddragon/img/perk-images/` are `.png`, not `.svg`
5. **Player-facing text says only what changes a decision.** Any string the player sees, in the app or exported to the League client, follows the `player-facing-text` skill (`.claude/skills/player-facing-text/SKILL.md`). Explain the why to the developer in chat, code comments and this file, never in the product.

## Image paths
- Champions: `/ddragon/img/champion/{DDkey}.png` (via `toDD()` sanitiser)
- Items: `/ddragon/img/item/{numericId}.png` (looked up from `item.json` at runtime)
- Runes: `/ddragon/img/{path}` where path comes from `runesReforged.json` flat map
- Stat shards: `/ddragon/img/perk-images/StatMods/StatMods{Name}Icon.png` (hardcoded SHARD_ICONS)
- Role icons: `/images/roles/position-{role}.svg`

### 26.20 data audit (2026-10-20)
It started with the user spotting Duskblade of Draktharr, an Arena-only item, in Volibear's build. That led to three systemic findings, and each now has a permanent guard.

**1. Items that cannot be bought on the Rift.** Duskblade of Draktharr (Arena, map 30; 43 slots) and Vigilant Wardstone (removed from the game, on no map; 50 slots across 13 supports and Ivern) passed every check, because every check only asked whether the NAME exists in Data Dragon. Both are replaced. `npm run check:items` now checks Riot's map-11 flag for every recommended item, and also that every name has a client export id in `lcuData.js`. That second check exists because `gen-lcu-data.mjs` only emits ids for names the roster used when it last ran. Yun Tal Wildarrows (now core for four ADCs) and Whispering Circlet were silently dropped from exported item sets until it was re-run. **Re-run `node helpers/gen-lcu-data.mjs` after any data edit that introduces a new item name.** **The ids sent are checked too (2026-10-22):** several items share a name across modes, and the id generator used to take the lowest id, so every exported set sent Stealth Ward 2056 (another mode's green-eye ward) instead of the Rift trinket 3340, plus Bloodletter's Curse 4010 (Rift: 8010) and Gargoyle Stoneplate 3193 (Rift: 663193). `gen-lcu-data` now prefers the map-11 id, `check:items` fails on any exported id that is not on the Rift, and the app's item images use those same ids. This was the "legacy item images" the user kept seeing. The patch workflow reports `check:items` into its PR body.

**2. The lolalytics Highest Win trap.** A plain WebFetch of a lolalytics build page returns its Highest Win tab, not Most Common, and presents that tab's rune page as the selected one, so builds "verified" that way record the wrong meta. Use the build-itemset endpoint instead (`https://a1.lolalytics.com/mega/?ep=build-itemset&v=1&patch=16.NN&c=<champ>&lane=<lane>&tier=emerald_plus&queue=ranked&region=all`, exact purchase orders), or the raw HTML's embedded `qwik/json`, which holds both tabs plus per-slot tables and gives unselected runes a `grayscale` class. `npm run audit:builds` (`helpers/audit-builds.mjs`) runs the endpoint over every role and flags any whose corePath does not open with the most common first item or first-two pair. The endpoint is unofficial, so the audit is report-only and stays out of CI. **Run it at the start of every patch sweep instead of trusting the per-batch notes above.**

**3. Drift.** The first audit run flagged 43 of 257 roles, many of them marked verified in the batch notes above (those predate 26.17-26.20, and some were read off the Highest Win tab). All are fixed except Pantheon Top and Mid (see below). The patterns:

### Matchup adjustments + class realignment (2026-10-20)
The user found the guide "falls flat" into some opponents, using Pantheon vs Mordekaiser as the example. Mordekaiser is a Juggernaut, like Darius and Garen, but he deals magic damage, so the Juggernaut page told Pantheon to buy Death's Dance (armor) and never mentioned magic resist. The per-class pages cannot express that, and only Pantheon had any per-opponent data (32 `champOverrides`, runes only).

**The fix is classes PLUS opponent traits** (the user chose this over hand-written matchup pages and over replacing the classes). `matchupAdvice()` reads the opponent's facts, each from a checkable source:
- **Damage type:** `damageTypes.js`.
- **Class:** `champClasses.js`.
- **Healing, shields and heavy CC:** `enemyTeam.js` `HEAL_CHAMPS` / `SHIELD_CHAMPS` / `CC_CHAMPS`, now exported. 28 self-healers and self-shielders were added, Mordekaiser included, and **each addition was checked against the champion's own ability text in `abilities.js`**. A first heal regex matched "health" as well as heals; use `heal(s|ed|ing)?`.
- **Health or armor stacking:** read from the opponent's OWN build in this app's data.
- **Range:** `ATTACK_RANGE` (Riot's `stats.attackrange`, emitted by `gen-lcu-data.mjs`; melee tops out at 225 and ranged starts at 300). `isRanged` lives in matchupAdjust, with Gnar and Jayce overridden to ranged because they lane in their ranged forms; gamePlan imports it. lcuExport used it for the lane start until the start data replaced those rules (2026-10-22).

From those facts it proposes:
- **Profile-aware resist swaps** (Death's Dance to Maw of Malmortius against magic damage, Steelcaps to Mercury's, and so on). A swap only happens when YOUR profile has an entry; an earlier profile-agnostic table offered AD Pantheon Banshee's Veil to Zhonya's.
- **Additions where nothing covers a need:** anti-heal, percent shred against health stackers, and Serpent's Fang for lethality builds against shields.
- **Same-row rune swaps, so a legal page stays legal:** Second Wind against ranged poke, Bone Plating against assassins, Unflinching and the Tenacity shard against heavy CC. None are proposed when a curated `champOverrides` page applied.

**UI (superseded 2026-10-21 by the game plan, below; the rune-swap button behaves the same):** a full-width strip under the champ-select "vs" readout shows the trait chips, item proposals with icons, and rune swaps with one button: "Apply + import" in champ select, "Apply to rune page" otherwise. It never changes a page unprompted. `sendToLeague(runesOverride)` exists for that one-click path, so its `onClick` usages must stay arrow functions; passing it directly would hand it the click event as a rune page. **Export:** when the opponent is known, the item set gains a "Vs <opponent>" block.

**Verified:** all 13,682 same-lane pairings were checked. Every proposed item is sold on the Rift and has an export id, no profile is offered the other damage profile's item, and no rune swap crosses a row. That legality check was confirmed to load all 45 rune rows and to separate rows 2 and 3. Proposals appear in ~51% of pairings for items and ~33% for runes.

Regression-tested against the pre-fix commit, where it reports exactly the four pages above.

**`champOverrides` = per-opponent rune pages (live since 2026-10-19).** Pantheon carries 32 of them (31 Top, 1 Support) — no other champion has any yet, so this only changes Pantheon until more are authored. How it works now: the champ-select opponent (`csOppDd`, auto-detected, or set by clicking an enemy in the **Enemy team panel**, the one place it is chosen: the "vs" readout is display-only since 2026-10-21, when the user ruled two pickers double control) is bridged into `matchupFoe` state — a bridge because `recommendedRunes` is computed near line 700, long before the champ-select state it depends on is declared — keyed on the display-name string so the 1.5s poll cannot re-fire it. `recommendedRunes` then merges the override over its class page. Overrides are PARTIAL, so they apply to the **primary build only**; alts are whole pages, and merging a fragment over a different tree would be illegal. `appliedMatchup` is non-null only when an override actually applied, so an opponent without one never resets a page the user edited. 24 of the 32 change the runes; 8 change only the advice text (their runes converged with the base after the 2026-10-19 row fix). **Auto-import fires once at pre-hover, before the opponent has usually locked**, so the client starts on the generic page; an "Import matchup build" button sits beside the "vs" readout for one-click import. It is deliberately not a second automatic import, which could overwrite edits made in the client — revisit only if the user asks for that.

### Game plan + boots timing (2026-10-21)
Two systems used to advise side by side: the lane advice (`matchupAdvice`, the strip under the "vs" readout and a "Vs <opponent>" export block) and the team readout (`analyzeEnemyTeam`'s "Consider" chips, on screen only). Pantheon into Mordekaiser with an AD-heavy team got Maw of Malmortius from one and Death's Dance from the other, with nothing saying which comes first. The owner's plan (2026-10-20): one recommendation ordered by game phase. **`gamePlan()` in `src/data/gamePlan.js` is now the only source**; the strip, the build card's core arrow and `buildItemSet` all call it.
- **Phases:** Lane = item 1 and the boots (in the champion's own order), plus the first defensive answer when behind; Mid game = the next two buys; Late game = the rest. Lane answers (`matchupAdvice` swaps and adds) come first; team answers (`teamThreats()` in enemyTeam.js: anti-heal, resist against the team's damage lean, Serpent's Fang for lethality into shields, Guardian Angel / Zhonya's / Randuin's against divers) form the mid and late layer. Capped at boots + 6 items; the overflow goes to Situational. Anti-heal against a sustain laner comes right after item 2; other damage answers after the core.
- **Ahead vs Even/Behind:** behind puts defensive answers right after item 1 and then every other buy (with no opponent this is exactly the old App.jsx `orderCore`, now in gamePlan.js); ahead keeps the authored damage order and puts defensive answers last. The export's Situational block now uses the class page's list for the CURRENT mode (it used to be the Ahead list whatever the switch said).
- **Conflicts:** when the lane opponent's damage and the team's lean want different resists, one line says so, e.g. "Maw for lane, Death's Dance for teamfights", and both items are kept inside the plan. In the test team (Mordekaiser, Lee Sin, Ahri, Jinx, Thresh = 3 AP, 2 AD) lane and team agree, so there is no note; with four AD teammates there is.
- **Export:** blocks are Start, First back, Lane, Mid game, Late game, Other boots, Situational, Vision (longest title still "Start vs Fiddlesticks", 21). The "Vs <opponent>" block is gone; `notes.plan` (phases with core / boots / lane / team tags, and the conflicts) feeds the in-game view, which accents the answers and shows the conflict line. `buildExport(..., foe, { mode, enemies })` takes the Ahead/Behind mode and the enemy team's locked picks; `sendToLeague(runes, enemies)` gets them from its caller and the auto-import from `modeRef` / `enemiesRef` (refreshed in the champ-select callback).
- **UI:** the "Consider" chips are removed from the Enemy team panel (which still sets the opponent); the plan strip under the "vs" readout shows the phases, the opponent's trait chips, swaps as "from → to", answers coloured by threat (orange = lane opponent, blue = their team), the conflict line and the rune-swap button. ## Desktop app
**Tray companion behaviour** (`electron/main.cjs`): the app runs from the Windows system tray (hidden-icons). Closing the window minimises to tray (`close`→`preventDefault`+`hide`), it does NOT quit — quit is only via the tray menu (which sets `isQuiting`). `window-all-closed` intentionally does nothing. Auto-launch at login is the OS login item (`app.setLoginItemSettings({openAtLogin, args:['--hidden']})`, only written when `app.isPackaged`); the `--hidden` arg makes the login launch start in the tray (`START_HIDDEN`). The poll loop watches `getCreds()` for a false→true transition (League client just launched) and calls `revealForLeague()` → `positionWindow()`: a **second monitor** if `screen.getAllDisplays().length>1` (centres on the non-primary display), else **docked to the right ~42%** of the single screen beside League. Tray icon is `electron/tray-icon.png` (regenerate via `node helpers/gen-tray-icon.mjs`). Renderer controls it via `window.frge.getStartup()/setStartup()` (Settings → Startup toggle).

Electron shell in `electron/main.cjs`. `npm run app` runs against built dist/; `npm run app:dev` loads the Vite dev server (run `npm run dev` first); `npm run dist:win` produces `release/Pantheon Guide Setup <ver>.exe` (installer) + `release/Pantheon Guide <ver>.exe` (portable). electron-builder uses `electronDist: node_modules/electron/dist` (its own download/rename step fails on this machine). NOTE: this dev environment sets ELECTRON_RUN_AS_NODE=1 — clear it before launching any Electron binary or `require("electron")` returns a path string and the app instantly exits.

- **Custom Build Studio + local profiles** (user vision, 2026-08-09 — pipeline, mostly client-only buildable now): let users author their OWN build (pick champion + role, edit the rune page — already editable — and assemble an item set: start / core / situational), name it, and save it. **Export as a shareable code**: serialise {champ, role, runes, items} to a compact versioned string (e.g. `FRGE1-<base64url(JSON)>`, or a packed binary for shorter codes) that pastes into Discord/chat; **import** parses it back. **Import to client** reuses the existing LCU pipeline (`buildRunePayload` + item set → `applyBuild` in `main.cjs`) — no new client plumbing. **Local storage FIRST** (no backend/auth needed): the Electron main process reads/writes build JSONs in a **`FRGE.GG` folder** — prefer a user-visible `Documents/FRGE.GG/builds/*.json` (fall back to `app.getPath('userData')`), via new IPC `frge:save-build` / `list-builds` / `load-build` / `delete-build`. **Local profiles** = multiple named local profiles (a folder each) holding saved builds + the prefs currently in `localStorage` (theme, favourite champ, startup, champ-select toggles) — the interim "profile" until real accounts exist. **Migration path:** when the backend + Riot RSO land (see Monetisation/accounts — the "secure way to create user profiles" the user is waiting on), sync these local builds/profiles to the cloud; store any tokens in Electron `safeStorage`, never `localStorage`. Build order: (1) local folder read/write + a Saved-Builds list, (2) the custom build editor, (3) the export/import code, (4) cloud sync once accounts exist.

- **Desktop auto-update — SHIPPED v0.7.0 (2026-08-07).** `electron-updater` + `electron-log` in `main.cjs`: `autoDownload=false`, checks on launch + every 6h (packaged only), emits status to the renderer over `frge:update`, IPC `frge:update-check/-download/-install/-state` + `frge:version`. The renderer shows an **Update pill top-right** (available → downloading% → Restart & update) and an **Updates row in Settings → General**. `quitAndInstall` sets `isQuiting` so the tray app exits to install. Config: `build.publish` = github Smiggul/pantheon-guide (the repo is now **PUBLIC**, so no token needed), which bakes `app-update.yml` into the package. electron-builder auto-bundles the prod deps into `resources/app/node_modules/` even though `files` is custom (verified). **Release process:** bump `package.json` version + roll CHANGELOG, `npm run dist:win`, then `gh release create vX.Y.Z --repo Smiggul/pantheon-guide --target frge-gg --notes-file <notes> "release/FRGE.GG Setup X.Y.Z.exe" "release/FRGE.GG X.Y.Z.exe" "release/latest.yml"`. **`latest.yml` MUST be attached** — it's what installed apps read to detect the new version. Auto-update only works from v0.7.0 forward (older installs need one manual update). Portable exe can't self-update; the NSIS installer is the updatable one. Still unsigned → SmartScreen warns until a cert is added.
- **Desktop auto-update** (original research 2026-08-06, now implemented above): use `electron-updater` (+ `electron-log`) — ~10 lines in `main.cjs` calling `autoUpdater.checkForUpdatesAndNotify()`; it fetches `latest.yml` (emitted by electron-builder next to the installer), compares to `package.json` version, downloads + installs on quit. **Windows auto-update needs the NSIS target (already built); the PORTABLE exe can't self-update** — so the installed/Setup build is the one to distribute. Blocker: the repo is **private**, so the plain GitHub-Releases provider would require shipping a GH token in every install (insecure). Hosting options, decision still OPEN: (a) a separate **public releases repo** holding only installers + `latest.yml`, source stays private (recommended — free, works with the `github` provider / `update.electronjs.org`); (b) **generic provider** → Cloudflare R2 / S3 bucket (free tier, full control, more setup); (c) embed a read-only token (NOT recommended). Signing: builds are unsigned, so SmartScreen warns on each update until a code-signing cert (or Azure Trusted Signing) is added — fine to defer for playtesting. Next step when resumed: pick a host, add `publish:` config + a release workflow (can extend the patch-update CI) that uploads the installer + `latest.yml` per version tag.

### Monetisation / accounts (planned — not built)
- **Ad slots**: 4 non-intrusive zones are already reserved in the layout (top banner, left + right side rails, collapsible bottom bar). They render as placeholders today; wire a real ad network later. Ads must stay non-intrusive — never overlay the build/rune workspace.
- **User login + accounts**: track users, sync their saved builds/preferences. Auth belongs in the Electron **main** process; store tokens with Electron `safeStorage` (OS keychain) — never `localStorage`. The Settings popout already has the entry point (an "Account" section with a Sign in / Sign up button that currently only shows a "coming soon" note — no credential capture, on purpose). Real auth is **backend-gated** and needs, roughly:
  - A small backend service (auth server + DB) — the app is currently a static SPA + Electron shell with **no backend at all**. Nothing real can be built client-only.
  - **Riot account linking = Riot Sign-On (RSO)**, which is an OAuth2 flow — but RSO access is **granted by Riot per-product and is heavily gated** (not open to hobby apps by default; requires an application/approval). Do NOT assume it's available; confirm approval before building the flow. RSO can return the user's **email** (with the right scope), which is the intended source for the mailing-list opt-in.
  - **Mailing list**: needs the backend to store the email + an email provider (e.g. a transactional/marketing service). Opt-in must be explicit (a checkbox), never auto-subscribe.
  - The user plans to prototype accounts/payments in a **separate project first**; treat this as scaffold-only here until that lands.
- **VIP subscription**: a paid tier that hides all ads. The UI already gates every ad zone behind an `isVip` flag, so switching it off is a one-line change once auth exists.
- **Payment gateways to evaluate**: Yoco and Ozow (both South-Africa-first, good local card/EFT support), PayPal (international). Decision deferred — the user plans to prototype this in a separate project first.
- **Security prerequisite**: before shipping login/ads, run CodeRabbit over the PR and add a Content-Security-Policy + render ad content in a sandboxed iframe (external ad scripts must never run in the main renderer).
